# HAIGURE SURVIVAL v2 T05-4 NPC・BIT標的選択個性 計画

更新日: 2026-07-29

## プロンプト

> NPCとBITのターゲッティングの優先順位について、現状は一度ターゲットしたキャラクターを、見失うなどの解除条件まで基本的に追い続けると思います。ただ、それだと目の前に他のキャラクターがいるのに、そちらを狙わないのが不自然な場合があります。
>
> 追いやすいキャラクターを狙う挙動も個体ごとの個性にしたいです。BIT生成時、およびNPCが洗脳された時に、50%ずつの確率で「最初に取得した標的を基本的に追い続ける個体」と「自分から最も近い標的へ常に切り替える個体」を発生させたいです。
>
> 実現可能性と実装方法を調査し、なるべく早く実装できるタスク配置を検討したうえで、今後のプランへ組み込んでください。
>
> NPCは毎フレーム視線を確認する必要はなく、BITと同じ10Hz、または性能を優先して5Hzで十分です。修正が簡易であればBITの探索周期も5Hzへ統一してください。
>
> 近くに標的候補が複数いる場合、探索ごとに標的が変わって経路計算が繰り返されないようにしてください。5Hz探索＋1秒保持と1Hz再探索を実際の状況で比較し、挙動がほぼ変わらず負荷が低いなら1Hz再探索を採用してください。
>
> 1Hz再探索でプランを練り直し、その内容で実装してください。
>
> 候補数が急減した場合まで同一個体の再探索間隔を厳密に1秒以上へ固定することは必須ではありません。1Hzは平常時の基準とし、一時的に1秒未満になることは許容します。個体別cooldownがすでに簡易な形で実装済みであれば、そのまま残して構いません。

## 確定方針

- 本機能は既存のNPC用`selectCombatTarget()`／`findNearestVisibleTarget()`と、BIT用の可視標的探索・CHASE維持処理を再利用できるため実装可能である。新しい全件総当たり探索や毎描画フレームの追加Rayは作らない。
- 共通の標的選択個性を`persistent`と`nearest-visible`の2種類に固定する。
  - `persistent`: 現行どおり、初回取得時の同距離候補は既存のframe／source順で決め、取得済み標的が有効である間は保持し、視認喪失、追跡断念距離、死亡・洗脳完了、到達不能など既存の解除条件まで追跡する。
  - `nearest-visible`: 自律visual標的が有効な間は1Hzで、距離・陣営・生存状態・遮蔽条件を満たす可視候補のうち現在位置から最も近い対象を選び直す。最短対象のIDが変わった場合だけ標的を変更する。
- 各個体は独立した50%／50%抽選を1回だけ行う。BITは生成時、NPCは初めて洗脳済み戦闘状態へ入る時に確定し、以後の状態変更、被弾、Follow／Leave、再捕捉で再抽選しない。初期洗脳済みNPCは生成時に確定する。
- 個性は既存乱数を消費せず、固定salt `haigure-v2:t05-4:target-selection:v1`、actor種別、個体IDをFNV-1a 32bitとMurmurHash3 `fmix32`で混合し、最上位bitで50%／50%を決める。同じactor種別・IDはゲームseedにかかわらず同じ個性となり、個性追加によって既存seedの初期配置、gun／no-gun、飛行、射撃時刻をずらさない。
- `nearest-visible`の同距離候補だけは距離の後に対象IDの昇順で決定し、配列順や空間索引の列挙順に依存させない。`persistent`の初回取得は既存契約と回帰を維持してframe／source順のままとする。別の1秒holdや距離ヒステリシスは追加せず、1Hz再探索自体を通常の自発的切替上限とする。
- 死亡、洗脳完了、対象消失、陣営不一致などRay不要の標的有効性は毎update確認する。現在visual標的の視線RayはNPC／BITとも5Hzのcredit式ラウンドロビンへ統一する。
- 標的なし、現在標的の無効化、視認喪失後の既存解除条件成立時は通常の1Hz期限を待たず、5Hz側の優先再取得枠へ入れる。強制標的の設定とRay不要の解除は即時とするが、Rayと経路計画の公平予算は迂回しない。
- `nearest-visible`の別候補全探索は1Hzの独立credit式ラウンドロビンとし、全個体を同じ更新へ集中させない。`persistent`は有効な現在標的を持つ間、この全探索を行わない。同じ更新で現在標的確認と別候補探索が重なった場合は現在標的の視線結果を共有する。
- 1Hzは平常時の負荷基準であり、候補集合が急変した特殊状況まで厳密保証する必須仕様にはしない。実装済みの単純な個体別1秒cooldownは残すが、この特殊状況のための追加機構は設けない。
- 候補は既存空間索引で絞り、距離順に視線Rayを行い、最初の可視候補で終了する。`nearest-visible`だけ同距離を対象ID順、`persistent`の取得は既存source順で決定する。
- AlarmのFIFO強制標的、外部Alert、公開処刑、hold、fixed、random、carpet編隊、Follower同期射撃など、既存の明示的な強制標的・固定攻撃状態は個性より優先する。強制状態を終えた後の自律的なvisual標的選択から個性を再適用する。
- carpet編隊中も各BITは固有の個性を保持するが、編隊中のFollowerは既存どおりLeaderの強制標的へ従う。編隊解除後は各個体の個性へ戻る。
- 自律visual標的のID変更では現在経路、BITのactive transition、戦闘mode、profile、射撃timerを同期的にclearしない。最新標的だけを経路更新待ちにし、NPCは既存の最低4計画／update・全要求0.5秒以内の公平予算、BITは既存のCHASE最大4計画／updateで再計画する。同一IDでは経路clearと再計画を行わない。
- 通常壁など視線を遮る対象の向こう側にいる近距離候補は選ばない。既存の視線契約で透過する窓・柵越しの候補は選択対象にできる。
- 旧挙動への互換wrapper、個性欠落時のfallback、未設定を暗黙に`persistent`へ読み替える分岐は追加しない。生成済み個体は必ず有効な個性を持つ契約に統一する。
- 診断は現在標的視線確認数、別候補探索数、候補Ray数、自発的／強制標的変更数、経路clear／再計画数をNPC／BIT別に公開する。固定`1/60`秒では99 NPCの5Hz確認を最大9件／update・1Hz探索を最大2件／update、50 BITを最大5件／最大1件とし、長いframeのcatch-upは現在確認最大20件、別候補探索最大4件で打ち切って残りcreditを後続更新へ送る。

## 実行単位と推奨設定

- 推奨ブランチ: `codex/v2-t05-4-target-selection`
- 推奨worktree名: `fps_survival20251226-t05-4-target-selection`
- 推奨モデル: GPT-5.6 Sol
- 推奨リーズニング: Ultra
- 選定理由: NPCとBITで異なる索敵予算・追跡状態を共有契約へ揃え、Alarm／Alert／固定攻撃の優先順位、決定的乱数、99 NPC／50 BIT性能を同時に維持する必要があるため。
- 開始条件: I0が`develop`へマージ済みであること。最新`origin/develop`から専用branch／worktreeを作成する。
- 並行可否: B04と別worktreeで並行可能。B04は学校生成正本、`.blend`、GLB、両NavMesh、カタログhashだけを所有し、T05-4は標的選択型、NPC／BIT Runtime、T05 fixtureだけを所有する。
- 統合条件: B04とT05-4は独立したPull Requestとしてレビュー・`develop`統合できる。T04-3Bは両方が`develop`へ統合された後に開始し、実学校で個性と動的扉・エレベーター・20室variantを同時回帰する。
- 全体計画所有: B04とT05-4の並行実装中は、両branchから`docs/plan.md`、`docs/plans/v2/next_tasks_plan.md`、`docs/branch_strategy.md`を編集しない。本I0 branchで依存と所有を先に確定し、各担当は自分の個別計画だけを更新する。

## 結果

2026-07-29、T05-4 Runtimeと回帰を実装した。共通の決定的50%個性を追加し、NPCは初回洗脳完了時、BITは生成時に`persistent`／`nearest-visible`を一度だけ確定する。既存乱数列は消費しない。NPC／BITの現在標的確認を5Hzへ統一し、`nearest-visible`だけを平常時1Hzで再探索する。標的なしの優先再取得、同一更新のRay共有、視線診断、自律変更と強制変更の分離、個体別cooldownを実装した。

自律的な標的ID切替では既存経路とBITの戦闘状態を同期clearせず、最新IDだけを既存の公平な経路予算へ接続した。Alarm／Alert、Follow／Leave、hold、fixed、random、carpet、公開処刑などの強制状態は個性より優先する。独立ソースレビューで検出した候補集合縮小時の共有credit偏りは、単純な個体別cooldownで修正した。最新指示に従い、候補急減時の厳密1秒保証を必須仕様へ広げる追加機構は設けていない。

T05実ブラウザ回帰は272／272 PASS、warning／errorは0件だった。NPC／BITとも同一更新で現在確認1件・別候補探索1件・Ray 1本を確認した。固定`1/60`秒の99 NPCは現在確認4950／4950件・別候補探索490／490件で全99体を巡回し、1更新最大9件・2件以内だった。50 BITは現在確認500／500件・別候補探索44／44件で全50体を巡回し、1更新最大5件・1件だった。99 BITの現在確認も4950件・全99体各50回で、catch-upはNPC／BITとも現在確認20件・別候補探索4件以内だった。NPC／BITのtargetless優先再取得は初回1秒で29／29体を一巡した。

自律ID切替では旧経路を同期clearせず、NPCは最新標的への経路1件、BITは切替更新と次更新を合わせて最新destinationへの経路1件だけを実行した。複数BITの同時切替も5／5体を2回の更新で公平に完了し、全5体が各自の最新destinationへ1回ずつ同期した。1更新の個性探索と全CHASE経路計画を各4件以内、alternative向け実経路計画を最大2件に維持した。

学校72遷移Contextの99体探索はp95 4.1ms／max 12.0ms、隣接帯追跡はp95 4.1ms／max 7.6ms、一斉標的喪失は1.2ms、後続60fps更新はp95 0.3ms／max 0.5msで既存予算内だった。`typecheck:t05`、`typecheck:v2`、`build:t05`、通常`build`、V2依存監査はPASSした。通常ゲームの実ブラウザでも学校3D空間、playing、NPC 99、BIT 55、BEAM 16を確認し、warning／errorは0件だった。通常buildには既知のBabylon.js 4MB超chunk警告だけが残る。

最終独立レビューでは、候補集合縮小時の共有credit偏りを修正した後のRuntimeと、全個体巡回、同距離規則、強制優先、最新destinationへの経路同期を再監査し、未解決のP1／P2がないことを確認した。変更9ファイルはUTF-8 BOMなしで、ローカル絶対パス、debug残骸、括弧不整合、`git diff --check`違反がない。
